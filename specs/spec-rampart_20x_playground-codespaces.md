# Rampart 20x Playground Codespaces Specification

**A GitHub Codespace launched from this repository runs the playground from the published TAP images and this repository's own boot record, with no tap checkout, so anyone with a GitHub account can open a running copy. The repository holds the whole launch: a devcontainer, a compose file and one boot record.**

This is an extension of `spec-rampart_20x_playground-v0.md`. It adds files at the repository root (`.devcontainer/`) and one boot record; it adds no bundle, page or code. Ruled by George, 2026-11-05: the launch lives in the plugin's own repository, so any plugin author can do the same for their own boot record, and nothing about a launcher lives in the tap repository.

### One-Click Launch
----
RID: `req-rampart-20x-playground-codespaces`

Status: `In Development`

#### Implementation

`.devcontainer/devcontainer.json` is compose-native: it attaches to the `web` service of `.devcontainer/docker-compose.yml`, which runs `tap-db` and the playground's product image, `rampart-20x-playground-web`, from `ghcr.io/unified-systems-com` (anonymous pull; pinned by digest, on tap v0.4.8). The product image carries this repository's `codespace` record at `/app/boot/codespace.boot.json` and every plugin the record installs, so nothing is mounted over the record and nothing is installed at start. The entrypoint of the published image does the rest when `CODESPACES=true`: it waits for the Codespace's name, derives the forwarded origin, the trusted-proxy header and the instance owner (the account that opened the Codespace, by numeric id, with role `tap_admin`), and selects the profile named by `TAP_CODESPACE_BOOT_PROFILE`. tap's initializer then gives the Codespace its own identity on its first start, the secret key, the database passwords and the grid id, in the `installation` volume. Then it builds the schema, runs `manage.py boot` once under the installation lock and serves. A named owner is the first admin, so no passkey enrolment link is issued.

The `codespace` record (`tap_plugin/rampart_20x_playground/boot/codespace.boot.json`) is the demo record's plugins and population with two changes: `profile_kind` is `deploy`, not `dev_local`, because the instance is served on a forwarded hostname and the dev passkey replay does not apply; and sign-in is the GitHub device flow that tap's own `codespace_demo` profile uses (a public client id, no secret, `owner_only`), so only the account that opened the Codespace can sign in. Its population sets `on_failure` `continue` for the reason below.

What a visitor sees first is the VS Code editor, not the playground; the playground is the forwarded port 8000, a separate address (observed 2026-11-16: the editor opened on `/app`, tap's own code and README in the image, a visitor took it for the instance, and `onAutoForward: openBrowser` opened no tab). So the visitor configuration does two things. Its `workspaceFolder` is `/welcome`, a read-only mount of `.devcontainer/welcome/`, which holds one file, a `README.md` that says the editor is not the playground and how to reach the site; `workbench.startupEditor` is `readme`, so the editor opens on it. And its `postAttachCommand` runs `.devcontainer/site-ready.sh` (mounted read-only at `/opt/playground/site-ready.sh`) each time an editor attaches: the terminal says the playground is starting, polls `http://127.0.0.1:8000/` inside the container with the image's `curl` every 5 s, and prints the forwarded address (built from `CODESPACE_NAME` and `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN`) when the site answers; after 20 minutes without an answer it says so and names this repository's issues page. The command is a script, not an inline string, because the terminal echoes the command line before its output (seen 2026-11-16: an inline command filled the terminal with shell text above the message). It runs nothing else and is not a boot. The repository README's Try it section gives the same steps. The maintainer configuration is unchanged: its editor attaches to `devbox` at `/workspace`, where port 8000 is not local.

A Codespace made from a prebuild resumes containers that compose created during the prebuild, when the Codespace had no name, so `web`'s environment carries an empty `CODESPACE_NAME` and the entrypoint used to refuse to serve (tap#1308). Both configurations therefore run `.devcontainer/codespace-identity.sh` as their `postStartCommand`, on every start: it waits for Codespaces' own `/workspaces/.codespaces/shared/.env` to hold the name and copies exactly three keys from it, `CODESPACE_NAME`, `GITHUB_CODESPACES_PORT_FORWARDING_DOMAIN` and `GITHUB_USER`, with one `printf` written in place, into `.devcontainer/codespace-identity.env`. `web` mounts that file at `/run/tap-codespace-identity.env` and names it in `TAP_CODESPACE_IDENTITY`, and tap's entrypoint (v0.4.5, `req-tap-serving-codespace-9`) waits up to 180 s for it and takes all three values from it over the environment. The shared file also holds `GITHUB_TOKEN` and `GITHUB_CODESPACE_TOKEN`; the script never copies them, and the compose file never mounts the shared file. In the maintainer configuration the script runs in `devbox`, through the `/workspace` checkout, and `web` sees only the three keys. In the visitor configuration `web` is itself the dev container, so Codespaces gives it `/workspaces` and with it the shared file, tokens included, whatever this repository does (see Known gaps); the script runs there, mounted read-only at `/opt/playground/codespace-identity.sh`.

What the published image needs that a checkout supplied, and how each is met without changing tap:

| Need | Why | How |
| --- | --- | --- |
| A writable `/run/tap-codespace.env`, and the identity file | The entrypoint writes the first; `postStartCommand` writes the identity; `/run` is root-owned in the image and the container user is not root | `initializeCommand` creates both files, mode 666, in `.devcontainer/` on the Codespace host, and the compose file mounts them; both are gitignored, and the identity is rewritten on every start, never committed or baked into an image |
| This Codespace's own secret key, database passwords and grid id | No secret may ship, and none may be made before the Codespace starts: a prebuild runs `initializeCommand` and starts the containers, so anything made then is shared by every Codespace built from it | tap's initializer (`req-tap-bake-hosts-5`, tap#1343) mints them into the `installation` volume at the Codespace's first start and re-keys the database away from the compose file's bootstrap password. The entrypoint waits for the Codespace's name before the initializer runs, and a prebuild has none. `initializeCommand` generates nothing |
| A writable `/app/logs` | The boot record is written there | a world-writable `tmpfs` mount (`mode=1777`; rootless Podman refuses a tmpfs `uid=`) |
| No venv or uv-cache volume | A product image runs the environment it ships, and its entrypoint refuses to start under a mount over `/app`, `/app/.venv` or `/app/tap-product` | none: the compose file mounts neither |
| No pre-migrate snapshot | The snapshot directory is under the root-owned `/app`, and a new database has nothing to keep | `TAP_BOOT_INSTALL__SNAPSHOT_BEFORE_MIGRATE=false` |
| The schema built from the models | Replaying every migration on a new database was the longest part of a launch (measured 2026-11-21 on a real Codespace at tap v0.4.1: see Known gaps). A Codespace's database is always new | `TAP_BOOT_INSTALL__SCHEMA_FROM_MODELS=true`: tap 0.4.2's entrypoint builds an empty database's tables from the models and records every migration as applied; a database that already has a schema is migrated normally |
| The collector step, in the first boot | tap's entrypoint starts the job workers before it runs `manage.py boot` (since tap v0.4.1), so the `fire-collector` step finishes inside the first boot with the preflight on and the default wait. Until 2026-11-21 the record turned the preflight off and gave the step `timeout_seconds: 20`, because on tap v0.3.3 the workers started after boot (observed 2026-11-13) | Nothing: the record carries the same collector step as the demo record |

The playground also publishes a **product image** (tap `req-tap-bake-product-image`): tap-web with the `codespace` record's whole environment, core and every plugin, built into the image, so a start installs nothing. `.github/workflows/publish-image.yml` is a thin caller of tap's reusable `bake-product-image.yml`. It names the record, the profile, the tap-web base by digest and the package, `ghcr.io/unified-systems-com/rampart-20x-playground-web`, and the reusable workflow verifies the base's attestation, builds on amd64 and arm64, tags the index `in-<inputs digest>` and `sha-<commit>` and attests it. It runs from `main` only. Both compose files pin the index digest of a run on `main`, so a change to the record publishes a new image that neither uses until a later change moves both digests to it.

`deploy/compose.yml` runs the same image on someone's own machine, from that one file and no checkout, with Docker or rootless Podman: `docker compose -f compose.yml up -d`. It is not a Codespace, so the Codespace derivation does not run; tap's initializer (`req-tap-bake-initializer`) gives the installation its identity instead. The file carries only a bootstrap database password; on the first start the initializer mints the secret key, the database role passwords and the grid id into the `installation` volume, re-keys the database away from the bootstrap value and prints one admin enrolment link (a passkey) to the web container's log. The port is bound to `127.0.0.1`, because rootless Podman otherwise publishes on every interface, and the origin is `http://localhost:${PORT:-8000}`. Sign-in is by that passkey; the record's GitHub device-flow provider is owner-only, and with no Codespace there is no owner.

#### Known gaps

- **The images are pinned by digest: the product image built on tap v0.4.8, and tap-db v0.4.8.** tap-db's digest is unchanged since v0.4.5. v0.4.8 puts the Codespace on tap's initializer road. Until the product image, `web` ran tap-web v0.4.5 with the record mounted. v0.4.0 never published (the release CVE gate failed on `tap-web`); v0.4.1 was the first release whose grid keys dimensions by Dimension node, which the plugin releases this record pins require; v0.4.2 adds the schema-from-models build the compose file turns on; v0.4.5 reads the Codespace identity file, which a prebuilt Codespace needs. Before these the pin was v0.3.3. Moving to a newer tap release changes `publish-image.yml` first; once its run on `main` publishes, both compose files move to the new product image digest and that release's tap-db digest (`docker buildx imagetools inspect`; the image tags carry no `v`).
- **The product image on the Codespace road was run locally, not yet in a real Codespace.** On 2026-11-23, this compose file with `CODESPACES=true`, a stand-in identity file and the port rebound to loopback served `302` 137 s after `compose up`, on this host with both images pulled: the derivation, the baked-environment checks, the schema from the models and `manage.py boot` all ran, and nothing was installed.
- **Host files are world-writable, and one is sourced by the entrypoint.** `initializeCommand` makes `tap-codespace.env` mode 666 because the host user cannot chown it to the image's uid, and the entrypoint writes and sources `tap-codespace.env`. In a Codespace the VM is single-user, so this adds no reach; a local Dev Containers launch on a shared machine would inherit the exposure. Accepted, recorded here.
- **`population.on_failure` is `continue` for the whole record.** It was set for the collector step that could not finish in the first boot on tap v0.3.3. That failure no longer happens; the policy is kept so a single failed step still leaves a visitor with a site, where `abort` would leave none. The boot engine has only a profile-level policy (`tap_boot/profile.py`).
- **The device-flow provider's self-test reports `secret` and `client_credentials` failed**, as it does for tap's own Codespace profile; the provider is declared non-critical.
- **The login uses the playground's own OAuth App**, "20x Playground" (`Ov23ctxWGaTmdJUM6ItQ`, owned by the unified-systems-com organization, Device Flow enabled), not tap's git-serious demo app, because GitHub names the app on the consent screen and the device page. A sign-in with it in a real Codespace was confirmed by the maintainer on 2026-11-21, on tap v0.4.1 and on tap v0.4.2: the device page and the consent screen both say "20x Playground".
- **Run in real Codespaces on 2026-11-21** (4-core machine, no prebuild). On tap v0.4.1, replaying every migration: the site answered 42 min 50 s after creation. On tap v0.4.2 with the schema built from the models: 6 min 43 s. The forwarded HTTPS origin, the private port and the device-flow sign-in worked in both. A restarted Codespace (a database that already has a schema) was not tried.
- **Run from a prebuild on 2026-11-22** (4-core machine, visitor configuration, tap v0.4.5, branch `spike/prebuild-timing` at the tree of this change). The prebuild took 12 min 56 s and succeeded. A Codespace created from it answered `302` on port 8000, through a `gh` port forward, 256 s after `gh codespace create` was called, where before tap v0.4.5 a prebuilt Codespace never served. Prebuilds are configured only on that branch, not on `main`, so a visitor's Codespace still builds without one; turning them on is the maintainer's call (it spends Actions minutes and storage).
- **In the visitor configuration `web` can read the Codespace's own tokens.** `web` is the dev container there, and Codespaces mounts `/workspaces`, with `.codespaces/shared/.env`, into the dev container. That is shown by the run above: the identity script reads only that file, tap's reader takes the name only from the identity file, and the site served. So the rule that the shared file is never mounted into `web` holds for the maintainer configuration, and for this repository's compose file, but not for what Codespaces itself gives a visitor's `web`. The token is the visitor's own Codespace token, in the visitor's own Codespace.

- **Why the maintainer box carries the `node` Feature.** The Codespaces agent reaches a container port that is not published on the host (here sshd's 2222) by running a bare `node` inside the container. The Debian base image has none, so `gh codespace ssh` timed out in the banner exchange while sshd was listening, and a stop and start did not help (10 of 10 attempts failed). Probed directly: a tunnel to remote port 2222 returned `exec: "node": executable file not found in $PATH`. With the `node` Feature pinned by digest, the first ssh attempt worked. This is the observed cause on this repository's overlay; it was not checked against tap's own dev box, whose identical overlay worked on 2026-09-22 (tap#778).
- **A plain `gh codespace ssh -- <command>` carries no GitHub credential**; run the command through a login shell, `bash -lc '<command>'`, to get the Codespace's `GITHUB_TOKEN` and the git credential helper. The token is the Codespace's own, scoped to this repository; what an agent should hold is tap#942's open design question.
